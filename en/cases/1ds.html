Case 01 · 1Doc

1DS: the 1Doc Design System

From visual identity to tokens in Figma, and from a library adapted from PrimeVue to a system that designers and AI evolve together, right in the code.

  • Design System
  • AI

Company

1Doc design team
Tools

01

Context

1DS was built in parallel with the platform redesign. It started as an adaptation of the PrimeVue library and, over time, the engineering team took over component development with the help of AI.

I share more about how 1DS was created and how it evolved in this article (in Portuguese) (opens in a new tab).

02

Foundation

I created the visual identity and the name of 1DS, defining its personality and communication standards.

I also structured the Figma libraries, creating the tokens and the relationships between them, to ensure consistency and flexibility as the interfaces evolved. Key deliverables included:

  • Organizing the primitive colors (primitive tokens) and the semantic color variants.
  • Creating the typography and shadow tokens.
  • Structuring the libraries and the component documentation standard.
  • Maintaining the components originally built from PrimeVue: adapting styles, applying tokens, and organizing their structure.

Before 1DS launched, I built all the components in Figma, applying properties and variables.

This structure created a consistent foundation for new components and for maintaining the interfaces. The Figma documentation is what made it possible to start developing 1DS with AI.

Over time, the process evolved: today the whole team uses AI and agents to build components, push changes, and update documentation. That’s what lets a lean, 4-person design team maintain and scale the system.

03

Challenge

As AI was adopted in development, the engineering team began implementing components with Claude Code through a specialized agent, and shipping the project via GitLab.

Because this process depended entirely on the engineering team, we hit a limit on how far and how fast the Design System could evolve.

04

Solution

Autonomy for the Design team

The solution was to give the Design team more autonomy: designers themselves started using the agents to maintain the code libraries, open merge requests (MRs), and take part directly in reviewing and approving changes.

A skill to bring code and Figma closer together

Along the way, I spotted another gap: components implemented in code didn’t always make it into the Figma libraries, creating a mismatch between the system used in development and the one available for designing interfaces.

To solve this, I built a Claude Code skill tailored to 1DS visual standards and guidelines. With it, you can:

  1. Build interfaces using existing components.
  2. Create new components that follow Design System conventions.
  3. Organize documentation in Figma using a predefined structure.

The skill is versioned in the project folder on GitLab and updated with every Claude Code working session, keeping its instructions in step with the system as it evolves.

Building components with AI

With the skills and agents in place, creating a component now follows a well-defined flow, from mapping the need all the way to shipping it in code and documentation:

  1. Map the need. Identify the component to be created and assess whether it belongs in the Design System and will be reused across screens.
  2. Research references. Look at how systems like Material Design, Carbon, Atlassian, and Animália solve the same component.
  3. Write a structured prompt. Describe the component clearly and in an organized way: purpose, anatomy, variations, states, and usage rules.
  4. Create it in Figma. Use the Figma skill together with the 1DS skill to generate the component following the system’s standards and create its documentation sheet.
  5. Review and refine. Review the component, test its usage, and apply Figma properties such as variants, booleans, and text.
  6. Bring it to code. Build the component in code with the 1DS development skill.
  7. Open the MR. Push the merge request to GitLab following the team’s defined steps, request review, and publish.
  8. Integrate and document. Bring the component into the Vue project and update the 1DS documentation.
05

Next steps

  • Review and improve components against accessibility criteria.
  • Expand usage guidelines, detailing each component’s properties, variants, states, and expected behaviors.
